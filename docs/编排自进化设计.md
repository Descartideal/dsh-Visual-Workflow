# 元编排最小自进化闭环与资产生命周期 V1 开发方案

## 一、开发目标

本阶段基于当前元编排架构，建立一个可以实际运行的最小闭环：

```text
历史经验
    ↓
wf_org_catalog
    ↓
父代理获得：
  1. Experience：过去编排中值得注意的经验（新增）
  2. Asset：可以参考的配置（角色、工作流，当前已有，但需要改造为读取资产，而非模板）
  3. 其他：规则、工具组合、模型等（不变）
    ↓
父代理生成本次任务的组织结构
    ↓
Workflow 执行
    ↓
执行结束
    ↓
检测到工作流运行 结束/失败，自动注入复盘提示词
    ↓
父代理复盘
    ↓
生成 Experience Candidate（渲染多项选择卡片）
    ↓
用户确认 / 修改 / 丢弃
    ↓
Experience DB（经验落盘数据库）
    ↓
下一次 Catalog 召回
```

同时建立独立的资产生命周期：

```text
用户编辑/创建模板（工作流模板、角色模板）
    ↓
用户确认“可复用”（属性栏渲染“入库”按钮）
    ↓
Active Asset（落盘为资产）
    ↓
Catalog 可召回（当前召回的是工作区模板，需要改造为召回资产）
    ↓
后续编辑
    ↓
新的 Version
    ↓
召回复用
```

资产历史版本全部保留，可以随时回滚。

本阶段的核心原则：

> **先让“经验闭环”和“资产生命周期闭环”真正跑起来**

# 二、V1 的持久化数据储存（SQlite）

## 1. Experience DB

职责：

> 保存执行复盘后形成、经过用户确认的可复用经验。

Experience 不是 Workflow，也不是运行日志。

它回答的是：

> “过去发生了什么？未来遇到类似任务时需要注意什么？”

### Experience V1 语义结构

```text
Retrieval
├── task_type
└── task_context

Experience Content（经验的完整内容）
```

### Retrieval 字段（用于向量检索）

`task_type`

用于粗粒度任务类型。

例如：

```text
软件开发
```

`task_context`

用于语义检索的自然语言上下文。

例如：

```text
面向消费者的移动端外卖平台 App 开发，包含用户端、商家端与订单流程。
```

它不是严格分类标签，而是未来向量/语义检索提供的检索锚点。

目标：

```text
编排任务
    ↓
父代理传入检索关键词
    ↓
Catalog工具 通过向量检索召回经验
    ↓
Top-K Experience
    ↓
父代理判断是否真正适用
```

向量检索只负责寻找语义相似候选。

**最终是否适用，由父代理进行语义判断。**

# 三、复盘

一次 Workflow 执行完成后的正确流程：

```text
Workflow Run
    ↓
父代理已有完整上下文
    +
Runtime 提供机器事实
    ↓
反思回顾
    ↓
0～N 个 Experience
    ↓
渲染多选提问卡片
    ↓
用户可多选值得入库的经验
    ↓
入库 Experience DB
```

## Runtime 提供机器事实（父代理通过上下文获取不到的运行事实）

Runtime 负责提供确定性事实，例如：

* token 使用（包含所有子代理）
* retry
* timeout
* 子代理总数量
* 上下文健康度（包含子代理）
* 执行时间
* 其他通过上下文获取不到但对复盘很有用的参数和运行事实

---

# 四、复盘 Prompt 的职责

复盘 Prompt 不应该要求：

> “总结本次任务。”

而应该要求：

> “从本次组织执行过程中识别未来可能具有参考价值的组织经验。”

建议复盘逻辑：

```text
1. 回顾任务上下文
2. 回顾初始组织形态
3. 回顾组织执行过程
4. 找出重要偏差
5. 分析 Action → Outcome
6. 生成 Experience
7. 检查是否过度泛化
8. 如果没有足够价值，可以返回 0 条
```

必须区分：

```text
Fact
Inference
```

例如：

```text
Fact：
子代理发生 context limit。

Inference：
因此本次采用 rotation/handoff 是合理的。

Experience：
当任务阶段较长且子代理接近 context limit 时，
可以采用结构化 handoff/rotation 保持阶段信息连续性。
```

不能简单因为：

```text
采用 A
+
任务最终成功
=
A 是好策略
```

而生成经验。

---

# 五、Experience

Experience 是未来组织生成时的参考知识单元，不是日志压缩，也不是完整 Run Summary。

总量控制在约 500 个中文字符以内，结构化表述。

其他规则：

* 允许 0 条
* 不强制生成经验
* 不复制长日志
* Insight 尽量是单句
* Evidence 只保留关键事实
* 语义重复应合并
* 不确定时宁可不产生

---

# 六、Asset 的职责

Experience 和 Asset 必须保持明确分工。

```text
Experience
= “这类任务过去发生过什么、以后需要注意什么”

Asset
= “这类任务可以参考什么组织配置”
```

例如：

Experience：

```text
长时间开发任务中，子代理接近上下文限制时，
提前进行结构化交接可以减少阶段信息丢失。
```

Asset：

```text
需求分析
    ↓
架构设计
    ↓
前端开发 ─┐
          ├→ 集成测试
后端开发 ─┘
```

因此 Catalog 每次召回的两个核心部分就是：

```text
Experience
    ↓
告诉父代理：
“这次编排需要注意什么”

Asset
    ↓
告诉父代理：
“有哪些组织配置可以参考”
```

这构成一次新编排的基础条件。

# 七、资产状态（用两个表来区分）

V1 只需要两个个生命周期状态：

```text
Active
Retired
```

### Active

当前正式可复用资产。

特点：

* 可以进入 Catalog
* 可以被父代理召回
* 是当前有效版本（默认最新版，可更改）

### Retired

历史版本保留但不再正常召回。

---

# 八、Active Asset DB

Active Asset DB 是：

> **Catalog 的当前可复用资产检索源。**

它不是完整资产数据库。

Catalog 从 Active Asset DB 获取资产索引并通过 id 召回相应资产的完整内容。

这样可以确保历史版本不会污染正常召回

---

# 九、Asset History DB

Asset History DB 保存：

> **所有正式资产版本，包括当前 Active 版本。**

例如：

```text
Asset A
├── v1
├── v2
└── v3 ← 当前 Active
```

Active Asset DB：

```text
Asset A → v3
```

如果回滚：

```text
用户选择 v1
    ↓
Asset History DB
    ↓
Asset A v1
    ↓
重新设为 Active
    ↓
Active Asset DB
    ↓
Asset A → v1
```

历史数据本身不被修改。

---

# 十、Asset ID 与 Version ID 必须分离

不要把版本直接理解为不同 Asset。

建议：

```text
asset_id
version_id
```

例如：

```text
asset_id   = frontend_development
version_id = v3
```

历史库：

```text
frontend_development
├── v1
├── v2
└── v3
```

Active DB：

```text
frontend_development → v3
```

因此：

> 回滚不是“复制旧资产”，而是“改变当前有效版本指向”。

具体数据库实现由现有项目技术栈决定，但必须保证这个语义。

# 十一、资产晋升（入库）

资产晋升是整个资产治理的核心入口。

```text
Template
  ↓
用户确认（点击入库按钮）
  ↓
Asset Version
  ↓
Active
```

登记时至少应该记录：

```text
asset_id（从模板变为资产后即固定）
version_id（后续更新递增该 id，比如 v1、v2）
source（来源）
created_at（创建时间）
update_at（更新时间）
```

其中 `source` 至少能够区分修改者（是谁创建的？是谁修改的？）

## 1. experiences — 经验表

```sql
CREATE TABLE IF NOT EXISTS experiences (
    id TEXT PRIMARY KEY, -- 经验唯一 ID，查询主键
    source_run_id TEXT, -- 产生该经验的那次工作流运行 ID（run id），用于回溯；可为空

CREATE INDEX IF NOT EXISTS idx_experiences_source_run_id ON experiences(source_run_id);
```

## 6. 写代码时要注意的几条语义（给 AI 开发的提示）

1. **事实源 vs 统计缓存**
   - 事实源：`workflow_asset_history.role_version_ids`。
   - 统计缓存：`role_asset_history.reference_status` / `reference_workflow_ids`。
   - 写入新工作流版本时，必须在同一事务里同步更新被引用角色版本的统计字段。

2. **引用统计的规则**
   - 按“角色版本”累计，不跨版本。
   - 新版本创建时，`reference_status='unused'`，`reference_workflow_ids='[]'`。
   - 一旦 `used` 不回退。

3. **回滚语义**
   - 回滚 = 修改 `*_asset_active.version_id` 指向历史表里的某个版本。
   - 历史表内容不变。

4. **版本号**
   - `version_id` 是整数，前端显示时加 `v`。
   - 新版本号 = 该 `asset_id` 下最大 `version_id + 1`。

5. **JSON 字段**
   - 所有 `*_json`、`*_schema`、`role_version_ids`、`reference_workflow_ids` 都必须是合法 JSON 字符串。
   - 写入前用应用层序列化，不要手拼字符串。


以上是暂定的表结构，还需要核实源码字段来核查并优化，判断这个表结构是否合适。主要是依据：wf_org_catalog 工具的召回信息来综合判定，同时还需要调整工具。关于全局唯一的查询主键 ID。要使用以资产前缀为命名的 ID 方便代理判断，比如：ex-*（经验资产id）、role-*（角色资产id）、flow-*（工作流资产id）。

## 资产去重机制说明（由于从资产转化为内联节点时的深拷贝解耦机制的影响，导致工作流资产储存时，会出现资产中重复一模一样的角色，因此增加去重机制）

每个角色资产或工作流资产在储存之前对已有的所有资产进行对比，当该新储存的角色字段 system_prompt 与资产中已存在版本角色相同字段一模一样的情况时，将已存在角色的 role_asset_type 字段从 standalone 或 inline 更新为 shared 然后在 reference_workflow_ids 字段中登记引用这个角色的工作流 id。

场景：当工作流资产保存时，其中的内联节点角色也会同步保存为角色资产。因此，当该角色资产与原本已登记过的角色资产重复时就需要去重。同理当从模板晋升成为资产时，如果该资产与已登记的工作流资产所产生的内联节点角色资产重复时，也会将角色资产类型变更为 shared。

最简单的区分：当一个资产被修改时，如果会触发多个资产的级联修改，它就必须是 shared 的。而 standalone 和 inline 只是来源不同，但他们修改时都不会触发级联效应。

需要说明：角色资产类型分为：standalone（独立角色资产）/inline（工作流的内联角色资产）/shared（多次引用的共享角色资产，涉及级联修改）。

standalone 即为直接由角色模版晋升而来的资产且该资产未被任何工作流资产登记引用过。
inline 即为直接由工作流模版晋升而带来的内联角色资产且该资产未被任何其他工作流资产登记引用过，也没有与 standalone 重复。
shared 被多个工作流资产登记引用过或 standalone 与 inline 产生重复。

这里说明一下，在资产登记入库时，standalone 与 standalone 发生重复，直接取消当次入库。inline 与 inline 重复，类型变为 shared。standalone 与 inline 重复，类型变为 shared。这是基于角色资产的判断。

如果工作流资产本身重复登记也会取消当次入库，这个直接在 ui 层面解决即可。下面细讲 ui 交互逻辑。
